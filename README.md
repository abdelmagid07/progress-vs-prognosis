# Progress Is Not Prognosis

Code and derived results for *Progress Is Not Prognosis: Local State and Eventual
Outcome in Long-Horizon Agents*.

The paper asks what a language model's internal state encodes while it runs as a
long-horizon software-engineering agent. It separates two things that are easy to
conflate: **how an execution is currently going** (local state) and **where it will
ultimately end** (eventual outcome). We find these are carried by different, nearly
orthogonal directions in the residual stream.

Concretely, the pipeline here:

1. Reconstructs a linear *value axis* by difference-in-means on in-context RL
   conversations, following prior work, and verifies it in the original single-turn
   setting.
2. Applies that axis **frozen, without refitting** to SWE-bench Verified agent
   trajectories generated by the same model, and measures what it does and does not
   separate.
3. Fits supervised probes to the same activations under matched-task, matched-prefix
   conditions, and recovers a distinct outcome direction.
4. Runs the leakage and confound controls that the main text and appendix report.

## Layout

| Path | Contents |
|---|---|
| `src/prognosis/axis/` | Value axis reconstruction and verification |
| `src/prognosis/single_turn/` | Single-turn coding control on DebugBench |
| `src/prognosis/agent/` | Agent rollouts, trajectory normalization, elicited confidence |
| `src/prognosis/extract/` | Activation capture and projection onto directions |
| `src/prognosis/analysis/` | Probes, statistics, confound and leakage controls |
| `src/prognosis/common/` | Paths and chat-template helpers |
| `tests/` | Offline wiring tests; no GPU or network |

| `configs/` | Model, agent, and task-selection configuration |
| `docs/` | Reproduction order and data provenance |

`docs/REPRODUCE.md` gives the end-to-end order and which stages need a GPU.
`docs/DATA.md` records what ships in this repository and what has to be regenerated.

## Setup

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e .          # add '[agent]' for SWE-bench rollouts
cp .env.example .env      # fill in an OpenAI-compatible endpoint
```

Model: Qwen3-32B in bfloat16, thinking enabled, throughout. Analyses index the
model's 64 transformer blocks; the axis carries 65 rows because its construction is
embedding-inclusive, so axis row `L+1` corresponds to block `L`. This offset matters
whenever a layer number is compared across the two.

## Reproducing the reported numbers

`docs/REPRODUCE.md` maps each reported result to the module that computes it and
the file that module writes. Activation extraction and rollout generation need a GPU
and are the only expensive stages; everything downstream runs on CPU.

## Relation to prior work

The value axis construction, the in-context RL dataset it is built from, and the
single-turn verification target all come from prior work on value representations in
language models, cited in the paper. That construction code and dataset are public:

- construction code: <https://github.com/nickjiang2378/value-axis>
- ICRL dataset: <https://huggingface.co/datasets/nickjiang/value-axis>

We reconstruct the axis on Qwen3-32B from that unmodified code and data, patched only
for memory and checkpointing. We do not refit it at any later stage. Two indexing
details differ from a naive reconstruction and are documented in `docs/DATA.md`.

Agent rollouts use `mini-swe-agent` on SWE-bench Verified; both are third-party and
pinned in `pyproject.toml`.
